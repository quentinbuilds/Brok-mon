The brief

What everyone is building

A small monster-catching game in the spirit of a 1998 handheld. One grassland map. Walk around, get jumped by a creature in the tall grass, fight it, throw a Capture Orb, keep it, open a menu and look at what you caught.

It runs on an Arduino UNO Q with a Modulino joystick, a Modulino 3-button block, and a small Waveshare display, on top of Summer Engine. That hardware is the whole reason the architecture looks the way it does — a tiny screen, four directions, three buttons, and no room for anything clever.

The PRD is blunt about priorities: playability > integration > game feel > visual polish > extra features. Nothing outside that list gets built until the loop runs start to finish. It also says, twice, don't over-engineer — this is a hackathon, not a codebase you'll maintain.

Your role

You are the plumbing, not a feature

The other five people build things a player can see: the map, the creatures, the fight, the catching screen, the menu art. You build the frame all of that plugs into — and you're the person who merges five branches into one build that actually runs on the device.

The PRD says this outright: "You should NOT spend the majority of your time making graphics." Five agents writing code simultaneously in one repo will collide unless the seams are decided before they start. Every hour you spend on a sprite is an hour those seams don't exist.

Concept 1 · The state machine

One state at a time, and it owns the screen

At any instant the game is in exactly one state, and that state owns two things: what the buttons do and what's drawn. This is what makes a three-button controller workable — pressing Button 1 means "start the game" on the title screen and "attack" in a fight, and the current state is what makes that unambiguous.

The rule that keeps six people out of each other's way: only the core switches states. The battle system doesn't reach over and put the game into the overworld. It announces that the battle ended, and you decide what happens next.

Every state implements the same four methods

This is the whole contract, and it's what lets you drop someone's screen into the machine without reading their code.

enter() — set up; runs once on arrival
update(delta_time) — one tick of logic
render() — draw the frame
exit() — tear down; runs once on leaving

delta_time is how long the last frame took. Systems multiply movement and animation by it so the game runs at the same speed whether the UNO Q is managing 60 frames a second or 20 — which it may well not be.

Concept 2 · Input abstraction

Nobody's game code touches the joystick

Gameplay code never reads the Modulino directly. It asks your InputManager "is up held?" and gets a yes or no. Only one file in the entire repo knows a physical joystick exists.

That single rule buys you four things, and the last one is the important one on a hackathon clock:

  • SpeedEveryone develops on a laptop with a keyboard on hour one, before the hardware is even wired up.
  • RemapButtons feel wrong on the real device? You change one file, not five people's code.
  • TestingA script can feed fake input and drive the game with nobody holding it.
  • No blockerThe PRD deliberately assigns no separate hardware workstream — hardware is treated as plug-and-play precisely because of this seam.

The API the PRD asks for

is_up() · held
button_a_pressed() · held
is_down() · held
button_b_pressed() · held
is_left() · held
button_menu_pressed() · held
is_right() · held
button_a_just_pressed() · edge
button_b_just_pressed() · edge
button_menu_just_pressed() · edge

Held vs. just-pressed is not a detail. is_down() is true on every frame the stick is held — right for walking. _just_pressed() is true for exactly one frame, on the transition from up to down — right for menus, so a single press moves the cursor one item instead of scrolling to the bottom of the list.

The physical mapping

No diagonals. The PRD asks for four-direction movement unless the hardware clearly supports better — grid-locked movement is also more faithful to the era.

Concept 3 · The event bus

Systems announce facts; they don't call each other

The PRD calls this "extremely important", and it's the single thing that decides whether integration at hour ten is calm or a fire.

Without it, the world code has to import the encounter code, which imports the battle code, which imports the catching code — and one person's rename breaks four branches. With it, a system shouts a fact into the room (PLAYER_MOVED) and whoever cares listens. Nobody imports anybody.

Here's the chain the PRD spells out — one loop of the game, crossing four people's code, with nothing directly wired to anything:

  1. 01 Person 2 · World Player takes a step. World fires PLAYER_MOVED
  2. 02 Person 3 · Encounters Hears it, checks the player is in grass, rolls the dice (5–10% per step, with a cooldown so you don't get two in a row)
  3. 03 Person 3 · Encounters Roll succeeds. Picks a wild creature and fires ENCOUNTER_TRIGGERED
  4. 04 You · Core Hears it and switches the state machine: OVERWORLD → BATTLE
  5. 05 Person 4 · Battle Battle state enters and fires BATTLE_STARTED

Notice step 4. The encounter system never says "go to battle" — it says "an encounter happened." You're the only one who moves the machine.

Concept 4 · Shared data

Three shapes everyone agrees on

These live in your core so nobody defines a second, slightly different version. Keep the fields exactly as the PRD lists them — it's what the battle, catching, and UI developers are all coding against.

Player
  • position, direction
  • movement_speed
  • sprite
  • party — max 3 creatures
  • inventory
Creature
  • id, name, type, sprite
  • max_hp, hp
  • attack, defense
  • catch_rate

e.g. 001 Emberfox · FIRE · 30 HP · atk 8 · def 5 · catch 0.35

Inventory
  • Capture Orb
  • Potion

Two items is enough for the MVP. Resist adding a third.

One legal note the PRD repeats in every section: original creatures and original assets only. No Pokémon names, sprites, or sounds anywhere in the repo.

Git rules you enforce

  • BranchesOne per system: feature/core, feature/world, feature/encounters, feature/battle, feature/catching, feature/ui.
  • RenamesNobody renames a shared file without telling you first. You're the integration owner — that's this.
  • PullsEveryone pulls from main often. Long-lived branches are how a 12-hour project dies at hour 10.
  • MergesMerge only when the feature works. Never commit build directories.
  • Always greenThe project must run continuously through the whole hackathon. If main is broken, that's your emergency.
The schedule

Four phases, in strict order

  1. P1 First 60–90 min You ship the skeleton. Game loop, state machine, InputManager, event bus, and empty stub states so the other five have somewhere to plug in. The stated goal: a player can walk around the world within 90 minutes.
  2. P2 Core gameplay The loop, end to end: walk → grass → encounter → battle → attack → catch → creature added → back to the overworld. Nothing else gets built until this runs.
  3. P3 Menu Party (with the active creature marked) and inventory (Capture Orb, Potion), navigable with three buttons.
  4. P4 Polish Only now: transitions, animations, sound, better sprites, battle effects, the startup sequence.
Hard stop · T-minus 2 hours

Stop adding features

No new mechanics. No new systems. No refactoring. No "one more cool idea." The last two hours are for integration, bug fixing, performance, testing on the actual device, visual polish, and preparing the demo. As integration owner this rule is yours to enforce, including on yourself.

Definition of done

The sequence that has to work unassisted

Not "the systems are built" — this exact run, on the physical UNO Q with its own joystick and screen, with nobody from the team touching anything.

BOOT→ TITLE→ OVERWORLD→ move→ enter grass→ random encounter→ BATTLE→ attack→ catch→ catching animation→ creature caught→ OVERWORLD→ open menu→ view party→ view inventory→ close menu→ keep exploring
